# SMP-21: coupon validation and coupons on Miguel orders — plan

Design: miguel `docs/superpowers/specs/2026-10-08-cfa-coupons-design.md`, section "WooCommerce plugin (SMP)".
Parent: SERGEN-36. The backend side (SM-498) calls these routes.

## What WooCommerce does today, and why it decides the shape

- `WC_REST_Orders_Controller::save_object` runs `calculate_coupons()` after `calculate_totals()`:
  `$order->apply_coupon()` → `WC_Discounts` → `recalculate_coupons()`, which rewrites every line's
  total. Passing `coupon_lines` through would discount Miguel's already-discounted lines a second
  time. So the plugin takes `coupon_lines` out of the payload before the controller sees it.
- `wc_update_coupon_usage_counts()` runs on the status hooks and sets
  `_recorded_coupon_usage_counts` the first time it runs, coupons or not. A coupon added after the
  controller has set the status is therefore never counted. So the coupon item is added inside the
  controller's flow, through `woocommerce_rest_pre_insert_shop_order_object` (before the first
  `save()`), with `discount` and `discount_tax` 0 — WooCommerce's own status hook then counts it.
- `WC_Discounts::is_coupon_valid()` returns `WP_Error('invalid_coupon')` for every failure; the
  numeric reason (105 not found, 106 usage limit, 107 expired, 108 min spend, 112 max spend, 102
  e-mail …) only reaches the `woocommerce_coupon_error` filter. The route listens on that filter
  for the one call and passes the number through as `error_code`.
- `WC_Coupon::is_valid_for_product()` returns false for any cart-type coupon (`fixed_cart`), so the
  per-line rule is evaluated on a copy of the coupon typed `percent` for those: the same
  include/exclude/sale-item rules, per line.

## Files

- `includes/class-miguel-coupon-validate-api.php` (new): `Miguel_Coupon_Validate_Api`, route
  `POST /miguel/v1/coupons/validate`, `Miguel_Rest_Auth_Trait`, `Miguel_Product_Code_Resolver`.
  - 400 `coupon.code_required`, `coupon.line_items_invalid` for a malformed request; the resolver's
    own 409 for an unknown or ambiguous product code.
  - Unsaved `WC_Order`: billing e-mail, `customer_id` of the user with that e-mail (per-user
    limits), one `WC_Order_Item_Product` per line with subtotal = total = price × quantity.
  - Refused: 422 `{error_code, message}` (message as plain text). Valid: 200 `{code,
    discount_type, amount, limit_usage_to_x_items, eligible_product_codes}`.
- `includes/class-miguel.php`: include, register, `register_hooks()`.
- `includes/class-miguel-order-create-api.php`: read and check `coupon_lines` (409
  `order.coupon_lines_invalid`), drop it from the WooCommerce payload, add the coupon items through
  the pre-insert filter for the one controller call.
- `tests/unit/test-coupon-validate-api.php` (new), `tests/unit/test-order-create-api.php`.
- `docs/openapi.yaml`, `CHANGELOG.md`, `readme.txt`; `bin/bump-version.sh 1.12.0`.

## Tests (written first)

Validation: each refusal (not found, expired, usage limit, e-mail restricted, min spend, max
spend) gives its own `error_code` and status 422; a valid percent coupon answers the 200 shape;
`eligible_product_codes` honours product include, product exclude, category include/exclude,
`exclude_sale_items`, and a `fixed_cart` coupon lists its eligible lines; a malformed request is
400; nothing is persisted (no order created).

Order create: with `coupon_lines` the order carries the coupon with discount 0, line totals and the
order total equal Miguel's prices (a 50 % coupon does not halve them), `usage_count` goes 0 → 1;
without `coupon_lines` nothing changes; a malformed `coupon_lines` is 409.
